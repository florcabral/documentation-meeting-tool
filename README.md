# Docs Decision Tool

A lightweight real-time web app for running structured documentation decisions during live remote meetings. Built with React + Vite, Vercel serverless functions, and Vercel KV — and paired with a Cursor AI layer that generates proposals, loads them into the app, and writes a decision record after the meeting.

---

## Background

The team holds recurring meetings to decide documentation structure — which pages to include, how to organise navigation, what belongs where. These meetings were painful:

- The facilitator drove everything from their screen. Others reacted rather than contributed.
- Voting happened in ad-hoc spreadsheets built on the fly. The output was a number, not a decision with reasoning.
- Not everyone felt represented. The loudest voices dominated.
- Nothing was recorded. The person running the meeting summarised from memory, losing nuance.

This tool replaces that process. Everyone gets the same URL, votes and comments from their own device, and the outcome is captured automatically.

---

## How it works

The facilitator prepares proposals before the meeting (written by hand or generated by Cursor). Teammates open the URL on any device — no account, no install. Everyone votes, comments, and proposes alternatives in real time. The facilitator's screen updates live. After the meeting, one Cursor command writes the full decision record to a local file.

```
before meeting      →      during meeting       →      after meeting
/propose or /review        everyone votes live          /summarize
writes session.json        comments + new proposals     writes discussion.md
```

## Features

### Proposals
- Proposals are loaded from `proposals.md` via the `/review` command, or generated from raw notes via `/propose`
- Each proposal gets its own tab — title, body, vote buttons, vote breakdown, and a comment thread
- Anyone can add a new proposal mid-meeting using the `+` button in the tab bar
- Anyone can edit a proposal's title and body inline using the Edit button on each proposal tab

### Voting
- `+1` / `-1` vote buttons on each proposal tab
- Aggregate score shown prominently (sum of all votes)
- Individual vote breakdown — who voted what — visible to everyone
- Clicking your active vote again clears it
- One vote per person per proposal — re-voting overwrites the previous vote
- No login: display name entered once on first interaction, stored in localStorage

### Term voting (overview tab)
- The overview tab includes a set of individual votable terms extracted from proposal bullet points
- Terms are presented as chips — click to vote `+1`, click again for `-1`, click again to clear
- Anyone can add a term manually using the "Add a term…" input below the chip grid
- The `/preferences` command reads the top-voted terms and synthesises a new cluster proposal from them

**Surfacing what the team actually cares about.** When teammates add new proposals mid-meeting using the `+` button, those proposals contain their own bullet points — concepts the facilitator didn't prepare. The **Refresh from proposals** button (facilitator-only) re-extracts terms from all current proposals and merges new ones into the chip set without resetting existing votes. This means the term grid reflects not just what was planned, but what the team raised during the discussion — making it a live signal of collective priorities rather than a pre-curated list.

**Term extraction** strips noise automatically: trailing qualifiers ("in real-time", "at scale"), matched parentheticals ("(OTA)"), leading action verbs before a proper-noun phrase ("Deliver Over-The-Air updates" → "Over-The-Air updates"), and compound bullets split on `&` and `and`. All chip labels are capitalised.

**Facilitator-only chip controls:**
- **Refresh from proposals** — pull terms from all current proposals and merge
- **Reset to original** — discard any added/refreshed chips and restore exactly the terms that were in `session.json` at load time
- **Delete individual chips** — hover a chip to reveal the `×` button

### Overview tab
- Cards for every proposal showing title, score, vote count, comment count, and a vote bar
- Updates live without interaction
- Leading proposal is badged

### Live updates
- App polls the API every 4 seconds
- New votes, comments, and proposals appear without a page refresh
- No websocket — polling is sufficient for a 5-person session

### Navigation
- A `← Overview` button appears alone in the left panel of the sticky header whenever you're on a proposal tab
- The app name stays centered; the button is always reachable without scrolling

### Facilitator role
- The `facilitator` field in `session.json` defines the admin display name (default: `"facilitator"`)
- Set your display name to match to unlock facilitator-only controls: chip deletion, refresh, and reset
- No passwords — the facilitator name acts as a lightweight trust signal suitable for a small internal meeting

## Cursor AI slash commands

Four slash commands form the facilitator's workflow. Each is wired as a `rule → prompt` chain in `.cursor/`.

| Command | When to use | What it does |
|---|---|---|
| `/propose` | Starting from scratch or raw notes | Paste raw context (notes, a Google Doc, a brief). Cursor generates 3–4 structured proposals as `proposals.md`, then runs `/review` automatically. |
| `/review` | Existing `proposals.md` is ready | Parses every `## ` heading as a proposal, extracts votable terms from bullet points, writes `session.json`. Run `curl -X POST http://localhost:3000/api/reset` to reload the app. |
| `/preferences` | Mid-meeting, after term voting | Fetches live term vote scores, synthesises a new cluster proposal from the top-voted terms, appends it to `proposals.md`, and runs `/review` automatically. |
| `/summarize` | End of meeting | Fetches the final vote state from Vercel KV and reads `session.json`, then writes `discussion.md` with the full decision record. |

### proposals.md format

`H2` headings become proposal titles. Everything below a heading (until the next `## `) becomes the proposal body. Bullet points become votable terms.

```markdown
# Landing page navigation — proposals

## Option 1: by customer need

Groups content by what problem the reader is trying to solve.

- Packaging & distribution
- Observability & monitoring
- Security & compliance

## Option 2: by lifecycle stage

Maps to the reader's journey from evaluation to long-term maintenance.

- Develop
- Build & publish
- Deploy
- Operate
```

## Suggested workflows

### Workflow A — proposals written in advance

1. Write `proposals.md` by hand (or from a previous meeting's `discussion.md`)
2. Run `/review` in Cursor
3. Start `npm run dev`, share the URL with the team
4. During the meeting: everyone votes, comments, adds proposals as needed
5. Run `/summarize` after the meeting

### Workflow B — proposals generated from raw notes

1. Collect raw context: paste notes, a Google Doc excerpt, or bullet points into Cursor
2. Run `/propose` — Cursor generates 3–4 structured proposals and loads them
3. Start `npm run dev`, share the URL
4. During the meeting: everyone votes, comments, adds proposals as needed
5. Run `/summarize` after the meeting

### Workflow C — using term voting mid-meeting

This workflow is useful when the team can't agree on which structural option to choose, but can agree on which concepts matter most.

**Suggested sequence:**

1. **Cluster voting first.** Start with the pre-loaded proposals. Let the team read, vote, comment, and add new proposals via `+`. This surfaces what's missing before term voting begins.
2. **Refresh terms.** Once the proposal set has stabilised, click **Refresh from proposals** on the overview tab. This re-extracts bullet-point terms from all proposals — including anything added mid-meeting — and merges them into the chip set without resetting existing votes.
3. **Add terms manually (optional).** Anyone can type a concept into the "Add a term…" input to add a chip for something not captured in any proposal body.
4. **Chip voting.** Direct the team to vote on individual terms. Each person votes independently on the concepts that matter to them.
5. **Synthesise.** Run `/preferences` in Cursor. It reads the top-voted terms and appends a new cluster proposal to `proposals.md`, then reloads it into the app automatically.
6. **Final cluster vote.** The synthesised proposal appears as a new tab. The team votes on it alongside the originals.

### Resetting the app between sessions

To clear all votes, comments, and proposals and reload from `session.json`:

```bash
curl -X POST http://localhost:3000/api/reset
```

The response confirms how many proposals and terms were loaded.

## Setup

### 1. Create a private GitHub repo

```bash
git clone <your-repo-url>
cd <repo-name>
```

### 2. Create a Vercel project + KV store

> Vercel KV has migrated to Upstash Redis. For new projects, add an Upstash Redis integration from the Vercel Marketplace — the `@vercel/kv` package is compatible with both.

1. Go to [vercel.com](https://vercel.com) → New Project → import the repo
2. Don't deploy yet — just connect it
3. Go to **Integrations** → search "Upstash Redis" → add free tier → Connect to project
4. Pull credentials locally:

```bash
npm i -g vercel
vercel link       # links local folder to the Vercel project
vercel env pull   # writes .env.local with KV credentials
```

`.env.local` is already in `.gitignore`.

### 3. Enable GitHub Pages

GitHub repo → **Settings → Pages → Source: GitHub Actions**

The deploy workflow is at `.github/workflows/deploy.yml`.

### 4. Install and start

```bash
npm install
npm run dev   # starts vercel dev — frontend + API functions + KV
```

## Data model (Vercel KV)

Keys are namespaced by session ID (date-based, from `session.json`):

| Key | Value |
|---|---|
| `session:{id}:proposals` | `[{ id, title, body, author, createdAt }]` |
| `session:{id}:votes` | `[{ proposalId, author, value, createdAt }]` |
| `session:{id}:comments` | `[{ proposalId, author, text, createdAt }]` |
| `session:{id}:terms` | `[{ id, label }]` |

Term votes use the same `votes` key — term IDs (`term--packaging`, `term--deploy`, etc.) are treated as proposal IDs for voting purposes.

## Constraints and non-goals

- **No auth** — display name is set once and stored in localStorage. Anyone with the URL can vote. The facilitator name is a trust signal, not a password.
- **No history** — one session per meeting. Past sessions are not browsable.
- **No markdown rendering** — proposal bodies are plain text. The Edit form is a plain textarea.
- **No GitHub integration** — `/summarize` writes `discussion.md` locally. No automated PR or issue creation.
- **Single session** — multiple concurrent sessions are not supported.
- **`proposals.md` is the source of truth** — the KV store is a cache. `/review` and `/reset` always reseed from the file.
